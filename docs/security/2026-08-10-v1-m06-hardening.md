# V1-M06 — hardening de app, VPS e Supabase

**Data:** 2026-08-10

**Base:** `origin/main` em `3f085ec7228d770649b0d9041f0e16154fe37629`

**Branch:** `codex/v1-m06-hardening`

**Escopo:** implementação local e auditorias somente leitura. **Nenhuma mudança em PROD.**

## 1. Decisões desta onda

- O armazenamento atual do JWT continua em cookie legível por JavaScript com
  fallback em `localStorage`. Removê-lo isoladamente quebraria o contrato Bearer
  e a sessão compartilhada entre superfícies. BAIXO-010 permanece aceito,
  válido e parcialmente mitigado; a correção definitiva exige sessão HttpOnly
  apoiada pelo backend e uma migração de login própria.
- O frontend passa a emitir globalmente:
  - `Content-Security-Policy: frame-ancestors 'none'`;
  - `Referrer-Policy: strict-origin-when-cross-origin`;
  - `Permissions-Policy: camera=(), geolocation=(), microphone=(self)`.
- A CSP é deliberadamente estreita nesta onda: bloqueia framing sem inventar
  allowlists de scripts, conexões, imagens ou PWA que poderiam quebrar o Next.
- O lockfile sobe somente o transitivo `nanoid` de 3.3.16 para 3.3.18, dentro
  do range já pedido pelo PostCSS, eliminando o único advisory de runtime.
- `backend/app/main.py` e `deploy/docker-compose.yml` não pertencem a M06 e não
  foram editados.

### Ordem segura para uma janela futura

1. Comprovar Browser Terminal/Emergency Mode no hPanel e mapear as três chaves
   autorizadas.
2. Criar usuário nominal, senha bloqueada, chave própria e `sudo`; provar login
   e `sudo -n true` em uma segunda sessão.
3. Manter uma sessão root aberta, criar drop-in reversível do sshd com senha
   desabilitada, `PermitRootLogin prohibit-password`, `MaxAuthTries 3`,
   `LoginGraceTime 30` e X11 desabilitado.
4. Rodar `sshd -t`, conferir `sshd -T`, recarregar — não reiniciar — e testar
   duas novas conexões.
5. Em mudança separada, instalar fail2ban ou aplicar rate-limit no SSH.
6. Só depois de migrar as automações, considerar `PermitRootLogin no`.
7. Aplicar updates e reboot em outra janela; validar SSH, firewall, nginx,
   Docker, containers, health e release ativa.

**Rollback:** manter a sessão original aberta; remover/restaurar o drop-in,
validar com `sshd -t` e recarregar. Se necessário, usar Browser Terminal,
Reset SSH ou Emergency Mode da Hostinger. Restore de snapshot é último recurso.

## 3. Supabase PROD — auditoria somente leitura

Projeto auditado: `pffafnchtxbimpwyaczq`.

### RLS sem policies

Quatro tabelas estão com RLS habilitada e zero policies:

- `password_reset_tokens`;
- `platform_admins`;
- `platform_audit_log`;
- `platform_orchestrator`.

Isso já é fail-closed para papéis sujeitos a RLS. As três tabelas de plataforma
também não têm grants para `anon`/`authenticated`; `password_reset_tokens`
mantém grants padrão, mas a RLS bloqueia o acesso. A migration proposta adiciona
uma policy explícita `using (false) with check (false)` somente quando a tabela
ainda não tiver nenhuma policy. O comportamento de acesso não é aberto.

### `current_igreja_id`

O advisor sinaliza `EXECUTE` para `authenticated` em uma função
`SECURITY DEFINER`. O estado coincide com a migration já versionada
`20260805_153000_security_definer_execute_hardening.sql`: esse é o único helper
tenant mantido para `authenticated`, pois as policies RLS dependem dele.
Revogar agora poderia zerar consultas legítimas. **Nenhuma migration nova foi
criada para essa função.**

### FKs sem índice

O advisor lista 51 FKs sem índice de cobertura. A distribuição estimada em PROD
é muito desigual:

- `agent_conversation_logs(conversation_id)`: aproximadamente 67.762 linhas;
- `messages(enviado_por)`: 36;
- `events(confirmado_por)`: 31;
- `pessoas(arquivada_por)`: 19;
- duas FKs de `conversations`: 2 linhas;
- as outras 45: estimativa zero.

Adicionar 51 índices agora aumentaria custo de escrita e multiplicaria índices
sem uso. A migration desta onda cobre apenas
`agent_conversation_logs(conversation_id)`, o caso material confirmado. Os 50
avisos restantes continuam registrados como INFO e devem ser reavaliados por
volume/consulta antes de nova escrita.

### Drift do ledger

- O repositório possuía 65 migrations SQL antes desta onda; M06 adiciona duas.
- O ledger nativo exibido pelo Supabase lista 26 entradas.
- A tabela `public.schema_migrations`, usada por
  `backend/scripts/apply_migrations.py`, **não existe em PROD**.

Consequência: o runner local não pode ser apontado para PROD. Ele trataria o
histórico inteiro como não aplicado, apesar de grande parte do schema já existir.
A reconciliação do ledger é uma missão separada, read-only primeiro, sem
backfill automático e sem reaplicar migrations históricas.

Para a migration transacional de policies, o mecanismo futuro proposto é
`apply_migration` da Management API do Supabase, com nome único e confirmação no
ledger nativo `supabase_migrations.schema_migrations`.

O executor da migration `CREATE INDEX CONCURRENTLY` fica **BLOCKED nesta
branch**: o SQL passou em PostgreSQL 17 com autocommit, mas ainda não foi provado
que `apply_migration` o executa fora de transação e registra o ledger. Até um
gate DEV separado comprovar o comando exato, ela não pode ser aplicada nem em
DEV nem em PROD. Também ficam proibidos como atalhos: SQL Editor,
`backend/scripts/apply_migrations.py` e `supabase db push`.

## 4. Gates DEV → PROD

1. Revisar e aprovar este PR; merge é gate separado.
2. Repetir advisors e preflight no Supabase DEV.
3. Confirmar no catálogo que a policy ainda não existe e que o índice de nome

4. Aplicar somente a migration de policies em DEV por `apply_migration` e

   funcional e advisor de policies resolvido.

   por `apply_migration` somente com autorização; exigir execução fora de
   transação e registro no ledger. Se for incompatível, voltar ao PR e escolher
   outra estratégia — não improvisar registro manual.
7. Depois dessa prova, aplicar o índice em DEV e confirmar definição exata,
   entrada no ledger, `indisvalid`, `indisready` e `indislive` verdadeiros.
8. Publicar o frontend em preview e testar login/logout/refresh em `app`,
   `admin` e `painel`, além dos três headers.
9. Repetir o preflight read-only em PROD. Aplicação em PROD exige autorização
   nova e explícita para cada migration.

    registrar falso sucesso.

## 5. Rollback

- Frontend: reverter o commit/deployment; os headers somem sem alterar sessão.
- Policies: uma migration reversa pode remover
  `service_role_bypass_only` das quatro tabelas. Com RLS mantida e sem outra
  policy, o comportamento volta ao mesmo default-deny anterior.
- Índice: remover `idx_agent_conversation_logs_conversation_id_fk` com
  `DROP INDEX CONCURRENTLY` em migration reversa standalone, após confirmar que
  não há operação dependente.
- `current_igreja_id`, grants, ledger, VPS e containers não são alterados por
  esta branch e não exigem rollback.
