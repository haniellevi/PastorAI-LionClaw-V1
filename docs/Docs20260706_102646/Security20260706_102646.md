## ALTO-003: Pipeline de verificação de sessão Clerk duplicado entre os dois resolvedores de auth
- **Severidade:** ALTO
- **Validação Cética de Qualidade:** CONFIRMADO — deps.py:95-111 (`get_current_user`) e :268-284 (`get_platform_admin`) repetem extração de bearer + verify/except (401) + lookup de `app_user`. A diferença deliberada (o platform admin NÃO chama `set_tenant_context` — linha 107 presente vs. docstring/nota :279 ausente) fica adjacente ao bloco idêntico, exatamente o cenário de drift descrito.
- **Arquivo(s):** backend\app\deps.py:95-118 (get_current_user) e backend\app\deps.py:268-288 (get_platform_admin)
- **Trecho:**
  ```python
  # get_current_user
  token = _extract_bearer_token(authorization)
  try:
      identity = clerk.verify_session_token(token)
  except ClerkAuthError as exc:
      raise HTTPException(
          status_code=status.HTTP_401_UNAUTHORIZED,
          detail="Sessão inválida ou expirada",
          headers={"WWW-Authenticate": "Bearer"},
      ) from exc
  app_user = db.execute(
      select(AppUser).where(AppUser.clerk_user_id == identity.clerk_user_id)
  ).scalar_one_or_none()
  ```
  ```python
  # get_platform_admin — bloco idêntico de token/verify/lookup
  token = _extract_bearer_token(authorization)
  try:
      identity = clerk.verify_session_token(token)
  except ClerkAuthError as exc:
      raise HTTPException(
          status_code=status.HTTP_401_UNAUTHORIZED,
          detail="Sessão inválida ou expirada",
          headers={"WWW-Authenticate": "Bearer"},
      ) from exc
  app_user = db.execute(
      select(AppUser).where(AppUser.clerk_user_id == identity.clerk_user_id)
  ).scalar_one_or_none()
  ```
- **Impacto:** É código de autenticação (extração de bearer, verificação do token e resolução do `app_user`) copiado nas duas entradas de segurança do sistema. A diferença intencional entre elas (o admin de plataforma NÃO chama `set_tenant_context` para operar em BYPASSRLS cross-tenant) está a poucas linhas de um bloco idêntico — um refactor futuro que "unifique" descuidadamente os dois caminhos, ou uma correção de hardening no fluxo de verificação aplicada só a um deles, cria janela para bypass de RLS ou de validação de token. Duplicação em lógica de auth é exatamente o cenário de "corrigir num lugar e esquecer no outro".
- **Recomendação:** Extrair um helper privado `_verify_and_resolve_app_user(authorization, db, clerk) -> (identity, app_user)` que encapsule extração+verificação+lookup, e deixar cada resolvedor apenas com sua parte específica (tenant context / billing gate vs. allowlist de plataforma). Assim a lógica sensível de verificação fica única, e a divergência deliberada (set_tenant_context) fica explícita e isolada.

## ALTO-004: Cobrança de SLA duplicada — marcador de dedupe não é durável em relação ao efeito colateral (envio WhatsApp)
- **Severidade:** ALTO
- **Validação Cética de Qualidade:** CONFIRMADO — em sla_engine.py o `send_text` (linha 280) ocorre dentro de `_dispatch`, antes do `session.commit()` de `run_for_igreja` (linha 254); `run_all_igrejas` faz `session.rollback()` (linha 372) em exceção, descartando o log de dispatch de cobranças já enviadas → `_already_dispatched` volta False e reenvia no próximo tick.
- **Arquivo(s):** backend/app/services/sla_engine.py:257-298 e 342-373
- **Trecho:**
  ```python
  def _dispatch(self, session, breach, instance) -> bool:
      evento = _dispatch_event_name(breach)
      if _already_dispatched(session, breach.igreja_id, evento):
          return False
      ...
      for phone in recipients:
          self._evolution.send_text(instance, phone, texto)  # efeito colateral JÁ ocorre
      self._log_dispatch(session, breach, evento, ...)        # apenas session.add()
      return True

  def run_for_igreja(self, session, igreja_id, now=None):
      ...
      for breach in breaches:
          if self._dispatch(session, breach, instance):
              handled.append(breach)
      session.commit()   # dedupe só vira durável AQUI, depois de todos os envios
  ```
- **Impacto:** O WhatsApp de cobrança/escalonamento é enviado ANTES do `session.commit()` que persiste o marcador de idempotência (`agent_conversation_logs.evento`). Se qualquer erro inesperado (não `EvolutionError`) ocorrer durante o loop de breaches, ou o `commit` falhar, o `run_all_igrejas` executa `session.rollback()` (linha 372) e descarta os logs de dispatch das cobranças que **já foram enviadas**. No próximo tick o `_already_dispatched` retorna `False` e as mensagens são reenviadas — cobrando o líder repetidamente. Um crash do processo entre o `send_text` e o `commit` produz o mesmo efeito. Isso viola a garantia "exactly one charge" descrita no próprio módulo.
- **Recomendação:** Tornar o marcador de dedupe durável antes (ou atômico com) o efeito colateral: gravar/commitar o registro de dispatch por breach ANTES do `send_text`, ou usar um INSERT idempotente (`ON CONFLICT DO NOTHING`) commitado antes do envio; alternativamente commitar por-breach dentro de `_dispatch`. Reduzir o escopo do `rollback` para não afetar dispatches já efetivados.

## MEDIO-003: Token de sessão (JWT, 8h) armazenado em localStorage — exposto a XSS
- **Severidade:** MÉDIO
- **Validação Cética de Segurança:** CONFIRMADO — auth-context.tsx:33 (`TOKEN_KEY`) e :77-84 (`writeToken` grava em `localStorage`); TTL de 8h confirmado em config.py:56 (`session_ttl_hours=8`). Mantida a severidade MÉDIO: o próprio finding já divulga honestamente que hoje não há vetor de XSS confirmado (React escapa, sem `dangerouslySetInnerHTML`), sendo defesa em profundidade — mas o padrão (JWT longevo em localStorage sem revogação ativa) é legítimo.
- **Arquivo(s):** frontend/src/lib/auth-context.tsx:33, :77-84
- **Trecho:**
  ```ts
  const TOKEN_KEY = "pastorai:token";
  function writeToken(token: string | null) {
    if (token) window.localStorage.setItem(TOKEN_KEY, token);
    else window.localStorage.removeItem(TOKEN_KEY);
  }
  ```
- **Impacto:** O JWT de sessão emitido pelo backend (TTL padrão de 8h — `session_ttl_hours=8`) fica em `localStorage`, acessível por qualquer JavaScript da página. Um único XSS permite exfiltrar o token e sequestrar a sessão por até 8 horas; como a revogação é apenas por status no banco, o token roubado continua válido até expirar. Não há refresh/rotação nem binding de sessão. (Nota: atualmente não há vetor de XSS confirmado no frontend — React escapa por padrão, sem `dangerouslySetInnerHTML` —, então o risco concreto hoje é de defesa em profundidade.)
- **Recomendação:** Preferir cookie `HttpOnly` + `Secure` + `SameSite=Strict` para o token de sessão, ou, se mantido no cliente, reduzir o TTL, adicionar rotação e reforçar CSP/mitigações de XSS. Avaliar mecanismo de revogação ativa (denylist de jti) para sessões comprometidas.

## MEDIO-005: `POST /broadcasts` não-idempotente com envio síncrono bloqueante → reenvio em massa em caso de retry/timeout
- **Severidade:** MÉDIO
- **Validação Cética de Qualidade:** CONFIRMADO — broadcasts.py:234-248: `create_broadcast` percorre `audience.recipients` chamando `send_text` de forma síncrona e só grava/commita o broadcast (`db.commit()`, linha 248) após o loop; não há chave de idempotência, então um retry do POST reenvia a toda a audiência.
- **Arquivo(s):** backend/app/routers/broadcasts.py:230-248
- **Trecho:**
  ```python
  instance = _instance(db, igreja_uuid)
  sent = 0
  if instance:
      for phone in audience.recipients:
          try:
              evolution.send_text(instance, phone, payload.mensagem)  # 15s timeout cada
              sent += 1
          except EvolutionError:
              logger.warning("Broadcast send failed to a recipient")
  ...
  db.commit()  # broadcast só é gravado depois de todos os envios
  ```
- **Impacto:** O disparo percorre toda a audiência de forma síncrona dentro do request HTTP, com timeout de 15s por mensagem. Para audiências grandes, o request excede facilmente o timeout do cliente/proxy; o cliente então re-submete o `POST`, que **não tem chave de idempotência** e reenvia o comunicado para toda a audiência (mensagens WhatsApp duplicadas para todos). Além disso, o `commit` do registro ocorre só depois dos envios: se o commit falhar, as mensagens saíram mas o broadcast não fica registrado, quebrando a contagem/histórico.
- **Recomendação:** Persistir o broadcast como `enviando` e commitar ANTES do loop; mover o disparo em massa para um worker/fila assíncrona (retornar 202); adicionar uma chave de idempotência (ex.: hash de titulo+mensagem+segmentos+janela de tempo ou id gerado no cliente) para bloquear reenvio duplicado.

## MEDIO-006: Webhook Asaas sem idempotência nem proteção contra entrega fora de ordem → status de assinatura pode regredir
- **Severidade:** MÉDIO
- **Validação Cética de Qualidade:** CONFIRMADO — subscription.py:304-313: aplica `map_payment_status(raw_status)` do último evento direto a `sub.status`/`igreja.status`, sem deduplicar por id de evento nem checar ordem/timestamp; um evento atrasado pode regredir `ativa`→`inadimplente`.
- **Arquivo(s):** backend/app/routers/subscription.py:258-315
- **Trecho:**
  ```python
  raw_status = obj.get("status") or payload.event
  new_status = map_payment_status(raw_status)
  ...
  if new_status is not None:
      sub.status = new_status
      if new_status == "ativa":
          sub.setup_pago = True
      igreja = db.get(Igreja, sub.igreja_id)
  ```

- **Impacto:** O handler aplica o último evento recebido diretamente ao estado, sem deduplicar por id de evento nem checar ordem/timestamp. - **Impacto:** Mesmo padrão do ALTO-004 (SLA), porém em canal de notificação. Como `get_subscription` (GET, chamado a cada abertura de tela) dispara `notify_autoupgrade`, se o `db.commit()` falhar após os envios, o evento `subscription_upgrade:<plano>` não é gravado e o próximo GET reenvia a notificação de upgrade aos admins. Efeito colateral (WhatsApp) não é atômico com o marcador de dedupe.
- **Recomendação:** Gravar/commitar o marcador de idempotência (INSERT idempotente do evento) antes de enviar, ou usar um flag persistido antes do disparo.
